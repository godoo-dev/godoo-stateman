# Phase 03.1: Multi-Odoo-version CI test matrix - Context

**Gathered:** 2026-05-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Make the existing acceptance suite genuinely pass on Odoo **17.0, 18.0, and 19.0** in CI. The matrix workflow already exists from quick task `260523-uda`; this phase closes the real gap — hardcoded `OdooVersion(17, 0)` call sites that prevent the 18/19 matrix entries from being meaningful — and updates docs + REQUIREMENTS to match.

**In scope:**
- Replace three `OdooVersion(17, 0)` hardcodes (src + tests) so the suite is version-aware
- Align ROADMAP success criteria with what actually exists in the repo (filename, test count)
- Re-anchor `VAL-03` in REQUIREMENTS.md to mean multi-version validation; move the LOC benchmark to a new ID
- Run the matrix on a sample PR; fix any genuine 17/18/19 test failures in-phase (no `skipif`/`xfail`)
- Update `PROJECT.md` and `CLAUDE.md` wording from "Odoo 17+" to "tested against Odoo 17.0, 18.0, 19.0"

**Out of scope:**
- Renaming `.github/workflows/test.yml` → `ci.yml` (decision: keep `test.yml` matching godoo-py)
- Per-Odoo-version schema-snapshot files on disk (not required for tests to pass)
- Postgres-version pinning per matrix entry (defer to testcontainer defaults; halt phase if Odoo 19 fails to start and upgrade `godoo-testcontainers` upstream)
- CLI surface changes (e.g., new `--odoo-version` flag on `plan` command)

</domain>

<decisions>
## Implementation Decisions

### Version propagation (the actual blocker)
- **D-01:** Add a session-scoped `odoo_version: OdooVersion` pytest fixture in `tests/conftest.py` (top-level, so both `tests/acceptance/test_plan_import.py` and `tests/acceptance/test_snapshot.py` can inject it). The fixture parses `ODOO_VERSION` env (default `"17.0"`) via the same regex-validation pattern used in `src/godoo_stateman/cli/commands/snapshot.py:61`.
- **D-02:** Rewrite `tests/acceptance/test_plan_import.py:135` (`_run_pipeline()` helper) to accept the `odoo_version` fixture instead of constructing `OdooVersion(17, 0)` inline. Every test that calls `_run_pipeline()` injects the fixture.
- **D-03:** Rewrite the three hardcoded `OdooVersion(17, 0)` sites in `tests/acceptance/test_snapshot.py` (lines ~45, 67, 85) to take `odoo_version` from the fixture. The literal `== "17.0"` assertions (lines ~49, 92, 94, 117, 126) become `== str(odoo_version)`.
- **D-04:** Fix `src/godoo_stateman/cli/commands/plan.py:90`: read `ODOO_VERSION` env using the same parsing pattern as `snapshot.py:61`. Inline-duplicate the ~5 lines (no new helper module this phase — extraction is a separate refactor if duplication grows).

### ROADMAP success-criteria realignment
- **D-05:** Keep workflow filename `.github/workflows/test.yml` (already exists, mirrors godoo-py). Amend ROADMAP SC-1 wording from `ci.yml` to `test.yml`.
- **D-06:** Amend ROADMAP SC-2 to drop the literal test count (`"18 @pytest.mark.integration tests"` → `"all @pytest.mark.integration tests"`). Future-proof against test growth. Actual count today is 19 (12 in `test_plan_import.py` + 7 in `test_snapshot.py`).

### Requirements (VAL-03) cleanup
- **D-07:** Rewrite REQUIREMENTS.md VAL-03 to mean "multi-Odoo-version validation: acceptance suite passes on 17.0, 18.0, 19.0 in CI matrix." Move the existing wording ("TS benchmark of 29 test files / 4,564 LOC") to a new `VAL-04` assigned to Phase 5. Update the traceability table accordingly. The ROADMAP Phase 03.1 line `Requirements: VAL-03 (multi-version validation)` stays correct after the rewrite.

### Failure policy for 18/19 shake-out
- **D-08:** Required-to-pass from day 1 on all three matrix entries. No `skipif`/`xfail`. If a genuine field-schema delta in 18/19 breaks a test, patch the test logic or the production code in-phase. Phase is not "done" until all three are green on a sample PR.
- **D-09:** If the shake-out reveals a `godoo-client` / `godoo-introspection` / `godoo-testcontainers` bug (upstream dependency), block Phase 03.1 — file an issue and PR upstream, pin a known-good version, then resume. Do NOT work around upstream bugs locally in stateman.

### Postgres pairing per Odoo version
- **D-10:** Accept `godoo-testcontainers` defaults for the Postgres image. Do NOT add a per-matrix-entry Postgres pin in this phase. If Odoo 19 fails to start because of PG version incompatibility, halt the phase and upgrade `godoo-testcontainers` defaults upstream (per D-09).

### Doc surface updates
- **D-11:** Replace "Odoo 17+" / "Odoo 17 CE is the primary target" wording in `PROJECT.md` and `CLAUDE.md` with "tested against Odoo 17.0, 18.0, and 19.0." Single canonical sentence reused in both files. The exact replacement string lands in the plan.

### Claude's Discretion
- Whether to extract the `ODOO_VERSION`-env parsing into a shared helper module is a follow-up refactor — for this phase, inline duplication between `snapshot.py` and `plan.py` is acceptable.
- The exact regex used in the fixture and in `plan.py` should match `snapshot.py:61` verbatim — Claude picks the snapshot version as the canonical reference.
- The fixture's location (top-level `tests/conftest.py` vs `tests/acceptance/conftest.py`) is Claude's call based on existing conftest structure; both acceptance test files need to see it.
- The order of work — fix hardcodes first, then run the matrix, then chase 18/19 failures — is operational and the planner can sequence as it sees fit, but the dependencies are: hardcode fix → matrix exercise → shake-out fixes → doc updates.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`snapshot.py:61` env-reading pattern** — regex-validates `ODOO_VERSION`, parses into `OdooVersion`, defaults to `"17.0"`. This is the template the new fixture (D-01) and the `plan.py` fix (D-04) both replicate.
- **Session-scoped `odoo` fixture in `tests/conftest.py`** — already exists and consumes the testcontainer harness via `TestHarness(snapshot=True)`. The new `odoo_version` fixture sits alongside it at the same scope.
- **godoo-py's `test.yml`** — copy-paste reference for any matrix tweaks (action versions, `setup-uv`, timeout-minutes). stateman's `test.yml` already mirrors it.

### Established Patterns
- **`ODOO_VERSION` env-var as the single source of truth for runtime Odoo version** — CI injects per matrix entry; testcontainer harness reads default `17.0` when unset. The phase extends this pattern to `plan.py` and the test fixture so the same env drives every consumer.
- **No per-test `skipif`/`xfail`** — phase policy (SC-2 + D-08). All version handling happens at the fixture/env-var layer, never per-test.
- **Upstream-first for godoo-py bugs** — pin known-good version + file issue + PR upstream, never work around locally (D-09).

### Integration Points
- The `odoo_version` fixture is the bridge between CI matrix and acceptance tests. CI sets `ODOO_VERSION` → fixture parses → tests use → snapshot/registry/plan code labels with the same version.
- `plan.py:90` is the only live (non-test) consumer of `OdooVersion` that's still hardcoded. After D-04 it joins `snapshot.py` as the second live consumer reading from env.
- REQUIREMENTS.md traceability table is the source of truth for VAL-03/VAL-04 semantics (D-07). Both ROADMAP and verification artifacts cross-reference it.

</code_context>

<deferred>
## Deferred Ideas

- **Extracting `ODOO_VERSION`-env parsing to a shared helper module** (e.g., `src/godoo_stateman/version.py`). Not justified by two call sites; revisit when a third live consumer appears.
- **Adding `--odoo-version` CLI flag to `plan` command** — explicit operator override would be nicer than env-only, but it's a CLI surface change, not in this phase's scope.
- **Per-Odoo-version schema-snapshot files on disk** (e.g., `tests/snapshots/{17,18,19}/`) — only needed if we start round-tripping snapshots through disk in tests; current tests are in-memory.
- **Per-matrix-entry Postgres pinning in stateman's `test.yml`** — only if the upstream fix in `godoo-testcontainers` (D-10) turns out not to be feasible.
- **Renaming `test.yml` → `ci.yml`** — explicitly rejected for this phase (D-05); revisit only if godoo-py renames first.

</deferred>
