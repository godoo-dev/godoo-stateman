## Summary

Phase 03.1 is a narrow precision-surgery phase: three categories of change, no new dependencies, no new modules. The CI matrix already exists (17.0/18.0/19.0 with `fail-fast: false` and `ODOO_VERSION` env injection), but every acceptance test that constructs an `OdooVersion` does so with the literal `OdooVersion(17, 0)`, making the 18 and 19 matrix entries structurally meaningless (they start a different container then run the same hardcoded version through the pipeline). This phase wires `ODOO_VERSION` through to every consumer.

The real uncertainty in this phase is the Odoo 18/19 shake-out: do the tests pass on a vanilla 18 or 19 CE base install? The answer depends on whether base-model fields the tests actually use changed between versions. The models used — `res.partner`, `res.country`, `ir.model.data` — are among the most stable in Odoo. The tests use a minimal surface (`name`, `email`, `active`, `country_id` on `res.partner`; `code` on `res.country`). The probability of breakage is low but non-zero and must be verified by actually running the matrix.

The `godoo-testcontainers` testcontainer harness reads `ODOO_VERSION` from `os.environ.get("ODOO_VERSION")` inside `container.py:99` and passes it to `normalise_odoo_version()`, which defaults to `"17.0"` when unset. This means the container startup is already version-aware. The gap is only in the stateman code that constructs `OdooVersion` for schema registry and snapshot assertions — those still hardcode `17.0`.

**Primary recommendation:** Fix all four hardcode sites (plan.py, test_plan_import.py, test_snapshot.py x3) → push a sample PR → triage any shake-out failures → update docs. This is a two-wave plan with Wave 0 as a guard-rail check.

## Research Finding 1: Exact snapshot.py:61 Parsing Pattern

[VERIFIED: codebase grep `src/godoo_stateman/cli/commands/snapshot.py`]

The canonical `ODOO_VERSION` parsing block occupies lines 61–66 of `snapshot.py`. Reproduced verbatim:

```python
odoo_version_str = os.environ.get("ODOO_VERSION", "17.0")
if not re.match(r"^\d+\.\d+$", odoo_version_str):
    raise typer.BadParameter("ODOO_VERSION must match N.N format (e.g. '17.0')")

parts = odoo_version_str.split(".")
odoo_version = OdooVersion(major=int(parts[0]), minor=int(parts[1]))
```

**Key details for the planner:**
- Default: `"17.0"` (the string, not a number)
- Regex: `r"^\d+\.\d+$"` — anchored, requires exactly one dot with digits on both sides
- Error: `typer.BadParameter("ODOO_VERSION must match N.N format (e.g. '17.0')")` — uses `typer.BadParameter`, not `ValueError` or `raise SystemExit`
- Split: `.split(".")` then `int(parts[0])`, `int(parts[1])` — keyword args `major=`, `minor=`
- The fixture (D-01) must NOT raise `typer.BadParameter` — tests don't have a Typer context; use `pytest.fail()` or `ValueError` instead. The regex and default are identical; only the error type differs.

**Fixture adaptation (D-01):**

```python
import os
import re
import pytest
from godoo_stateman.schema.version import OdooVersion

@pytest.fixture(scope="session")
def odoo_version() -> OdooVersion:
    odoo_version_str = os.environ.get("ODOO_VERSION", "17.0")
    if not re.match(r"^\d+\.\d+$", odoo_version_str):
        pytest.fail(f"ODOO_VERSION must match N.N format (e.g. '17.0'), got: {odoo_version_str!r}")
    parts = odoo_version_str.split(".")
    return OdooVersion(major=int(parts[0]), minor=int(parts[1]))
```

Note: `pytest.fail()` aborts collection; `ValueError` would surface as an error in the fixture call. Either works; `pytest.fail()` gives a cleaner CI message.

**plan.py adaptation (D-04):**

```python
import re
from godoo_stateman.schema.version import OdooVersion

# Inside _plan_impl, replacing line 90:
odoo_version_str = os.environ.get("ODOO_VERSION", "17.0")
if not re.match(r"^\d+\.\d+$", odoo_version_str):
    console.print("[red]ODOO_VERSION must match N.N format (e.g. '17.0')[/red]")
    return 1
parts = odoo_version_str.split(".")
odoo_version = OdooVersion(major=int(parts[0]), minor=int(parts[1]))
registry = SchemaRegistry(client, odoo_version)
```

Note: `plan.py` uses `console.print()` + `return 1` for all errors (not `typer.BadParameter` — the command uses `asyncio.run()` bridge). The error message should match snapshot.py's wording for consistency, but does not have to — it is an inline duplicate and differences are acceptable per D-04.

## Research Finding 5: Fixture Placement — conftest.py Layering

[VERIFIED: codebase read `tests/conftest.py`]

The current `tests/conftest.py` is at the root of the `tests/` directory. It contains one fixture:

```python
@pytest.fixture(scope="session")
async def odoo() -> TestHarness:
    async with TestHarness(snapshot=True) as h:
        yield h
```

The acceptance tests live in `tests/acceptance/`. There is no `tests/acceptance/conftest.py` (not found in the glob results).

**Conclusion:** The `odoo_version` fixture belongs in `tests/conftest.py` (top-level), co-located with the `odoo` fixture. This is correct per D-01. Reasons:

1. Both `test_plan_import.py` and `test_snapshot.py` are under `tests/acceptance/` and both need the fixture.
2. pytest fixture resolution walks up the directory tree from the test file to find conftest.py files. `tests/conftest.py` is visible to all tests under `tests/`.
3. If placed in `tests/acceptance/conftest.py`, it would not be visible to unit tests under `tests/unit/` — but unit tests do not need `odoo_version`, so either location would technically work. Top-level is cleaner.

**Fixture scope:** `scope="session"` is correct. `ODOO_VERSION` is set as a job-level env var in CI (not a per-test env var), so it cannot change within a session. Session scope matches the `odoo` fixture scope, which is important because `odoo_version` is consumed alongside `odoo` in the same tests.

**Pytest-asyncio note:** The existing `odoo` fixture is `async` and session-scoped. The new `odoo_version` fixture is synchronous (it only reads `os.environ` and calls `re.match`). No `async` keyword is needed. No `pytest-asyncio` interaction required.

## Research Finding 6: godoo-testcontainers Version Propagation — Source-Verified

[VERIFIED: codebase read `../godoo-py/packages/godoo-testcontainers/src/godoo/testcontainers/container.py:99`]

```python
async def start(self) -> StartedOdooContainer:
    odoo_ver = normalise_odoo_version(os.environ.get("ODOO_VERSION"))
    ...
    odoo = DockerContainer(f"odoo:{odoo_ver}")
```

```python
def normalise_odoo_version(raw: str | None) -> str:
    """Normalise ODOO_VERSION into dotted form. None/'17' → '17.0'."""
    if not raw:
        return "17.0"
    if "." in raw:
        return raw
    return f"{raw}.0"
```

**Confirmed:** The testcontainer already reads `ODOO_VERSION` from the environment and starts the correct `odoo:{version}` Docker image. When CI sets `ODOO_VERSION=18.0`, the container pulls `odoo:18.0`. When `ODOO_VERSION=19.0`, it pulls `odoo:19.0`.

The Postgres image is hardcoded to `postgres:15-alpine` (container.py line ~135). This is the default that D-10 says to accept. No stateman-side change required.

**The existing conftest.py `odoo` fixture does NOT pass `ODOO_VERSION` explicitly** — it relies on `os.environ` already having it set, which is correct. The fixture calls `TestHarness(snapshot=True)` with no `odoo_version` argument because `OdooTestContainer.start()` reads the env directly.

## Research Finding 10: Failure Protocol for Odoo 19 Container Start Failure (D-10 + D-09)

[VERIFIED: container.py source; ASSUMED for Odoo 19 / Postgres compatibility specifics]

### What the testcontainer does

When `ODOO_VERSION=19.0`, `OdooTestContainer.start()`:
1. Calls `normalise_odoo_version("19.0")` → `"19.0"`
2. Starts `PostgresContainer("postgres:15-alpine", ...)` — hardcoded image
3. Starts `DockerContainer("odoo:19.0")` — version-parametric
4. Waits for `_wait_for_odoo_ready()` with `startup_timeout=300s` (5 min default)

If Postgres 15 is incompatible with Odoo 19 (e.g., if Odoo 19 requires PG 16+), the Odoo container will fail to initialize the database and the `_wait_for_odoo_ready()` loop will exhaust all 150 attempts (`300 // 2`), then raise `TimeoutError`. The Odoo container logs are dumped to the logger at `ERROR` level before the exception propagates.

### Halt-and-Upstream Protocol (D-09 + D-10)

If this happens:

1. **Evidence collection:** CI logs will show the Odoo container logs (container.py:220–224 dump). Look for PG version error messages from Odoo 19 init.

2. **Diagnosis:** Confirm whether the failure is PG-version incompatibility vs. something else (e.g., image pull failure, Docker resource limits in CI runner).

3. **Upstream action:** File an issue on `godoo-dev/godoo-py` → `godoo-testcontainers` requesting a `postgres:16-alpine` default for Odoo 19. Write a PR that makes the Postgres image selection version-aware (e.g., `odoo_ver >= "19.0"` → `postgres:16-alpine`).

4. **Pin known-good:** While upstream PR is pending, pin `godoo-testcontainers` to the current `0.2.0` in stateman's `pyproject.toml` (it is already at `0.2.0`, so this is a no-op unless a new version shipped). The actual fix is in upstream, not in a stateman workaround.

5. **Phase blocked:** Phase 03.1 is marked blocked in STATE.md. The 17.0 and 18.0 matrix entries that pass are not declared "done" — all three must be green (D-08).

6. **Resume:** Once upstream merges and publishes a new `godoo-testcontainers` version, bump the constraint in stateman's `pyproject.toml` and re-run the matrix.

**Practical note:** If `odoo:19.0` does not yet exist on Docker Hub as of this phase execution, that is a different failure (image pull failure). CI will log a Docker pull error. In that case, block and document — Odoo 19 may not have a stable Docker image yet. The planner should include a "check Docker Hub for `odoo:19.0`" task in Wave 0 or as a pre-flight check.

## Common Pitfalls

### Pitfall 1: Over-editing `test_version_mismatch_on_load`

**What goes wrong:** The planner includes "convert all `== "17.0"` to `== str(odoo_version)`" without reading the test carefully. `test_version_mismatch_on_load` constructs a JSON payload with `"odoo_version": "17.0"` — this is the test fixture, not an assertion about the current Odoo version. Changing it would break the test semantics.

**How to avoid:** The task description must name the specific lines that change and the specific lines that do not. See §Research Finding 4 for the annotation.

**Warning signs:** If `test_version_mismatch_on_load` starts failing after the edit with a `VersionMismatchError` when it should have raised it, check whether the JSON payload was changed.

### Pitfall 2: `_run_pipeline()` callers not updated

**What goes wrong:** The `_run_pipeline()` signature is updated to accept `odoo_version` but 1–2 calling tests are missed, causing a `TypeError` on the session-scoped fixture invocation.

**How to avoid:** The task must enumerate all callers. There are 7 callers in `test_plan_import.py` (identified in §Research Finding 4). Each needs the fixture parameter added to its signature and passed through.

**Warning signs:** `TypeError: _run_pipeline() missing 1 required positional argument: 'odoo_version'`

### Pitfall 3: `odoo_version` fixture scope mismatch with `odoo` fixture

**What goes wrong:** The `odoo` fixture is `scope="session"`. If `odoo_version` is `scope="function"`, pytest will raise a scope mismatch error when a session-scoped fixture (`odoo`) is used in the same test as a function-scoped `odoo_version`.

**How to avoid:** `odoo_version` must be `scope="session"` to match `odoo`.

**Warning signs:** `ScopeMismatch: You tried to access the function scoped fixture odoo_version with a session scoped request object`

### Pitfall 4: Odoo 19 Docker image not yet available

**What goes wrong:** `odoo:19.0` tag does not exist on Docker Hub; CI fails with image pull error.

**How to avoid:** Add a Wave 0 pre-flight task to verify `docker manifest inspect odoo:19.0` succeeds. If the image does not exist, block the phase and document.

**Warning signs:** CI step `Run integration tests` fails in the first ~30 seconds with `Error response from daemon: manifest for odoo:19.0 not found`

### Pitfall 5: `re` module not imported in `plan.py`

**What goes wrong:** The D-04 fix adds a `re.match()` call but `import re` is missing from `plan.py`'s imports. The `snapshot.py` pattern works because `re` is already imported there.

**How to avoid:** Check `plan.py` imports before applying the fix. Current `plan.py` imports do NOT include `re` (verified — only `asyncio`, `os`, `pathlib.Path`, `typer`, and godoo/stateman modules).

### What Counts as "All Three Green"

A matrix entry is green if and only if:
1. The CI job exits 0
2. pytest reports `N passed` with no failures, errors, or skipped tests (beyond any legitimately skipped — but D-08 forbids `skipif`/`xfail`)
3. The job's test count matches the expected count (currently 19 integration tests)

### False-Positive Detection

A matrix entry that "passes" but collected 0 tests is a false positive. Detection:

- CI output will show `0 passed, X deselected` — this is not green.
- The pytest command uses `-m integration` which selects only `@pytest.mark.integration` tests. If no tests are collected, pytest exits 5 (`no tests ran`), which the CI `run:` step treats as non-zero → job failure. So a 0-collection false positive self-reports as a failure.
- However, if the marker filter matched some but not all tests due to a conftest issue, the count would be lower than 19. The planner should document the expected count (19) in the verification checklist.
